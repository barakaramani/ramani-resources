# Ramani leads: one record per person

Every form on the Ramani resources site posts to `/api/lead`. This function makes sure
a person is stored once, however many forms they fill in and on whatever device.

## Rules

1. A person is matched by email OR phone. Phones are stored as +255XXXXXXXXX, so 0712 345 678,
   712345678 and +255 712 345 678 are the same person. Emails are stored in lower case.
2. If someone first gave only a phone and later only an email, and then both together,
   the two records are merged into one.
3. One time actions are kept once per person: newsletter, community join (Biashara Tanzania),
   free tool contact, registration, alerts, bank access review, data room request,
   and each download or notify me item.
4. Other actions (quote requests, button requests) are kept every time, linked to the same person,
   so the person is still counted once as a lead.
5. Agent and bank referrals are matched on the client's phone. The same client can be referred once.
6. The reply tells the page `{ ok, duplicate, person_id, person_status }`, and the page shows
   "We already have your details, so nothing was added twice."

## Set up on Cloudflare Pages

1. Create the database: `npx wrangler d1 create ramani-leads`
2. Create the tables: `npx wrangler d1 execute ramani-leads --remote --file=schema.sql`
3. In the Pages project: Settings, Functions, D1 database bindings, add `DB` pointing to `ramani-leads`.
4. Put `functions/api/lead.js` in the repo at that same path.
5. In the site config set `RAMANI.endpoint = "/api/lead"`.
6. Add a rate limiting rule for `/api/lead` in Cloudflare (for example 20 requests a minute per IP),
   and Turnstile on the forms if spam shows up.

## Useful queries

People this month: `SELECT COUNT(*) FROM people WHERE first_seen >= '2026-11-01';`
New leads by first action: `SELECT first_type, COUNT(*) FROM people GROUP BY first_type;`
Everything one person did: `SELECT type, received_at FROM submissions WHERE person_id = ? ORDER BY received_at;`

# Uliza Ramani (the AI assistant) and SemaCall

## What is in this folder

| File | What it does |
|---|---|
| `functions/api/uliza.js` | The site assistant. It calls Claude with four tools that run Ramani's own calculator, so every number comes from Ramani and not from the model. It removes phone numbers and emails before anything reaches Claude, and it saves questions for content ideas. |
| `functions/api/brief.js` | For staff only. It works out a person's MQL score from everything they did and writes a call brief for the BDM. |
| `functions/api/semacall/push.js` | For staff only. It sends a scored lead and its brief to a BDM's SemaCall queue. |
| `functions/api/semacall/webhook.js` | SemaCall calls this after every call and incoming SMS. It gives back a call summary, the outcome, the stage, the next step and a Kiswahili SMS draft. When a customer replies STOP, ACHA or SITAKI, they are opted out of marketing SMS. |
| `functions/api/semacall/send-sms.js` | For staff only. It sends an SMS draft only after a BDM approves it, and never to someone who has opted out. The SMS goes out through Ghala (SemaCall only if Ghala is not set up). |
| `functions/api/sms/ghala-events.js` | Ghala calls this with customer SMS replies and delivery reports. Replies get the same handling as SemaCall: STOP, ACHA or SITAKI opts the person out, anything else gets a Kiswahili reply draft for a BDM to approve. Failed and delivered SMS are marked on the record. |
| `lib/core.js`, `lib/kb.js` | The same calculator, search, glossary and MQL score that the website uses. These are generated by the site build, so do not edit them by hand. |
| `lib/semacall.js` | The only file that knows SemaCall's API. Fill it in when SemaCall shares its documentation. |
| `schema_v2.sql` | Adds the MQL score, stage, owner and opt out fields, plus the calls and questions tables. |

## Setup

1. Run `schema_v2.sql` once, the same way as `schema.sql`.
2. Add these secrets in the Pages project:
   - `ANTHROPIC_API_KEY`
   - `ANTHROPIC_MODEL`: the Claude Haiku 5.5 model ID, from the Claude models page.
   - `ANTHROPIC_MODEL_SMART`: the Claude Sonnet 5.5 model ID, used for briefs and call summaries.
   - `SEMACALL_WEBHOOK_SECRET`, `SEMACALL_API_BASE`, `SEMACALL_API_KEY` and `SEMACALL_SENDER`.
   - Optional: `TURNSTILE_SECRET`.
3. Protect `/api/brief*`, `/api/semacall/push*`, `/api/semacall/send-sms*` and the sales desk page with Cloudflare Access, using your Ramani Google accounts. Do not protect the webhook. It checks the shared secret instead.
   Then add two Cloudflare variables from that Access application: `ACCESS_TEAM_DOMAIN` (for example `ramani.cloudflareaccess.com`) and `ACCESS_AUD` (the Application Audience tag). The code checks the signed Access token itself, so a faked header is refused. Until both are set, every staff route answers "staff_only" and stays closed.
4. In the site config set `RAMANI.brainEndpoint = "/api/uliza"`. The assistant then uses the Claude API instead of the demo.
5. Add a Cloudflare rate limit on `/api/uliza`, for example 10 questions a minute per IP.

# SMS through Ghala

All SMS go out through **Ghala** (ghala.io), with the approved sender name RAMANI. SemaCall stays for calls; it only sends SMS if Ghala is not set up. To force one, set `SMS_PROVIDER` to `ghala` or `semacall`.

- **Outbound:** an SMS leaves only after a BDM approves the draft on the sales desk. Nobody who replied STOP, ACHA or SITAKI is ever texted, and the same draft can not be sent twice.
- **Replies and delivery reports:** Ghala posts them to `/api/sms/ghala-events`. The request must carry Ghala's signature, so nobody else can opt people out or fake replies. The same reply is never counted twice.
- **One record per person:** replies are matched by phone (stored as +255...), so an SMS reply lands on the same person as their website form, emails and calls.

## Files

- `lib/ghala.js`: the Ghala client, the phone format and the webhook signature check.
- `lib/sms.js`: picks the provider, sends approved SMS, and handles replies from Ghala or SemaCall.
- `functions/api/sms/ghala-events.js`
- `db/schema_v4.sql`: stores Ghala's message id on each sent SMS so delivery reports can update it.

## Setup (Calvin)

1. In Ghala, get the SMS API key and register the sender name **RAMANI**.
2. In Ghala, go to Developer > Events, add `https://www.ramani.io/api/sms/ghala-events` for SMS replies and delivery reports, and copy the signing secret.
3. Run `db/schema_v4.sql` once.
4. Add these Cloudflare secrets: `GHALA_SMS_KEY`, `GHALA_SENDER_ID` (RAMANI) and `GHALA_WEBHOOK_SECRET`. Optional: `GHALA_PHONE_FORMAT` (`local` for 0712345678, the default, or `intl` for 255712345678).
5. Do not put `/api/sms/ghala-events` behind Cloudflare Access. It checks Ghala's signature instead.
6. Test with Ghala's sandbox numbers before going live: +255 700 000 001 (delivered), +255 700 000 002 (failed) and +255 700 000 003 (invalid number).

## To confirm with Ghala

Ghala's public docs show only one SMS example, so these points are built on our best reading and are marked "confirm" in `lib/ghala.js`. Only that file changes if Ghala says otherwise.

1. Phone format: 0712345678 (as in their example) or 255712345678?
2. What the send response looks like, and which field holds the message id.
3. The event names and fields for an SMS reply and for a delivery report, and whether they are signed with `X-Ghala-Signature` like WhatsApp events.
4. Whether the SMS API accepts an `Idempotency-Key` header, so a retry never sends twice.
5. How long sender name registration takes, and the price per SMS at Ramani's volume.

# Email through Resend (Amazon SES as a fallback)

The website sends its own emails through **Resend**, which Ramani already uses. Amazon SES is still in the code as a fallback. Every email lives in the same database as leads, SMS (Ghala) and SemaCall calls, so one person is still one record.

The code picks the provider by itself: Resend when `RESEND_API_KEY` is set, otherwise SES when the SES keys are set. To force one, set `EMAIL_PROVIDER` to `resend` or `ses`.

## What it does

- **Automatic emails** when someone fills in a form:
  - a welcome email for the newsletter
  - a download link
  - a thank you after the importer survey
  - a free tools welcome

  They go in Kiswahili when the person used the site in Kiswahili.
- **Newsletter page for staff** (`admin/newsletter.html`): write the email in plain text, preview it, send yourself a test, choose who gets it (everyone, MQLs, leads, customers, by language or by region) and send. It sends in batches of 40 and shows progress, and nobody gets the same campaign twice. Each send carries an idempotency key, so a retry never emails the same person twice.
- **Consent rules:**
  - Marketing emails go only to people who ticked consent.
  - Emails people asked for, such as a download link, go to anyone who gave an email.
- **Unsubscribe:** every email has an unsubscribe link and Gmail's one click unsubscribe header.
- **Suppression:** permanent bounces, suppressed addresses and spam complaints come back from Resend through a signed webhook. Those addresses are never emailed again.
- **Limits:** Resend allows 10 requests a second; the sender waits and retries when it hits that. If the daily or monthly quota runs out, the newsletter pauses and the rest stay waiting, so the campaign can be resumed later without anyone getting it twice.

## Files

- `lib/resend.js`: the Resend client and the webhook signature check.
- `lib/email.js`: templates, the consent checks and the provider choice.
- `lib/segments.js`: who each newsletter goes to.
- `functions/api/email/resend-events.js`: bounces and complaints from Resend.
- `functions/api/email/unsubscribe.js`
- `functions/api/email/campaign.js`
- `functions/api/email/send-batch.js`
- `db/schema_v3.sql`
- `site/admin/newsletter.html`
- SES fallback only: `lib/ses.js`, `lib/sigv4.js`, `functions/api/email/ses-events.js`.

## Setup with Resend (Calvin)

1. In Resend, add and verify the domain **news.ramani.io**. Add the DNS records Resend shows (DKIM, SPF and the return path MX) in Ramani's DNS, plus a DMARC record. Sending from a subdomain keeps newsletter reputation apart from staff email on ramani.io.
2. Create an API key with **Sending access** only, limited to news.ramani.io.
3. In Resend, go to Webhooks and add `https://www.ramani.io/api/email/resend-events` with the events `email.bounced`, `email.complained` and `email.suppressed`. Copy its signing secret (it starts with `whsec_`).
4. Run `db/schema_v3.sql` once.
5. Add these Cloudflare secrets: `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET`, `EMAIL_FROM` (for example `Ramani <news@news.ramani.io>`), optional `EMAIL_REPLY_TO` (for example `hello@ramani.io`), `EMAIL_SECRET` (any long random text, used to sign unsubscribe links) and `SITE_URL`.
6. Protect `/admin/*`, `/api/email/campaign*` and `/api/email/send-batch*` with Cloudflare Access. Do not protect `/api/email/unsubscribe` or `/api/email/resend-events`.
7. Check the plan: Resend Free allows 100 emails a day and 3,000 a month, which is enough for the automatic emails while testing. A weekly newsletter to the whole list needs the Pro plan or higher.

## Setup with Amazon SES (only if Ramani ever moves off Resend)

1. In SES, verify **news.ramani.io**, add the DKIM, SPF and DMARC records, and request production access.
2. Create an IAM user whose only permission is `ses:SendEmail`, with an access key.
3. Create a configuration set with a Bounce and Complaint event destination going to an SNS topic, and subscribe `https://www.ramani.io/api/email/ses-events?token=YOUR_SNS_TOKEN`.
4. Add `SES_REGION`, `SES_ACCESS_KEY_ID`, `SES_SECRET_ACCESS_KEY`, `SES_FROM`, `SES_CONFIG_SET`, `SES_SNS_TOPIC_ARN`, `SNS_TOKEN`, and set `EMAIL_PROVIDER` to `ses`.
